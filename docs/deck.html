Know which queries can leave Databricks
before they do.

Nirvana runs every query on Databricks and on Zetaris against the same data, compares the answers row by row, and keeps a rewrite only when it returns the exact rows.

Nirvana · Open Agent Hackathon 2026 · github.com/subheeksh5599/nirvana
The problem

A migration fails on answers, not on syntax.

The push

Azure Databricks Standard workspaces are being moved to Premium from 1 October 2026. Zetaris puts the increase at 35% or more per workspace.

The risk

A query that runs on a new engine can still return a different answer: a DECIMAL read as DOUBLE, 7 / 2 = 3, NULLs sorted to the other end of a top 10.

The gap

Table diffs prove the data moved. Nobody proves, query by query, that the workload still gives the same answers, and which rewrite fixes the ones that do not.

How it works

Four steps. Every one executed.

01Align the inputs

Both engines profile every table: row count, and per column non-null count, MIN, MAX and an exact SUM. A query over a table that differs is blocked, not judged.

02Run on both

The same query runs on Databricks and on Zetaris Lightning, which reads the parquet files in place.

03Compare every row

Results become canonical tokens with exact decimals and a SHA-256 fingerprint. A changed value is named by its column.

04Prove the cause

Rewrites run on Zetaris until one returns the source's exact rows. Otherwise the query stays on Databricks.

The guarantee

No verdict comes from a model.

A model may only propose SQL. The judge runs the proposal on Zetaris and keeps it only if its rows equal Databricks' rows.

A proposal with the right shape and the wrong rows is refused (test_wrong_advisor_rewrite_is_refused). An offline model ends a query in "keep", never in a guess.

Sponsor technology, load-bearing

Remove any one and a step stops.

Zetaris · the data layer

The 24 parquet files are Lightning filestore tables, read in place. Every query, table profile and rewrite runs through the REST SQL endpoint. One federated query across local disk and S3 shows which rows differ between two copies.

Meterless · H-MEM and Nightshift

H-MEM stores each proven fix and each order-tie proof with its query features. Matching queries try recalled fixes first and skip re-runs already settled; a fix that fails loses confidence. Nightshift is the only AI provider, on 127.0.0.1:8088, under the 0.90 provider contract.

NVIDIA Nemotron

Nightshift relays rewrite proposals to a free Nemotron for differences no rule explains. No local model runs. The judge decides on the rows.

Engineering

Built to be checked.

1,230 tests

Real SQL on DuckDB, the real H-MEM engine, every TPC-DS query parsed and qualified, tampered tables caught, property tests on the canonicaliser.

Receipts

Each run gets a SHA-256 over query hashes, both fingerprints, verdicts and rewrites. Importing an edited recording is refused.

A dashboard, not a slide

Start a run, watch 24 tables and 103 queries fill in live, open any query to its rows, fingerprints, rewrite and every execution step.

Honesty

What this is, and what it is not.

Declared pre-existing work

None of our own: Nirvana was started during the hackathon. Third-party parts used unchanged: Meterless H-MEM (vendored at 1742dec), the 103 TPC-DS texts from Apache Spark (3153f1e), DuckDB's dsdgen for the data, the Zetaris docker platform.

Limits

Results over 100,000 rows are truncated and marked. Rules cover four causes; anything else goes to the model or ends in keep. Nirvana reports verdicts and timings; it makes no dollar claim of its own.
